## 1. Edit Mind 用户案例

### 1.1 个人媒体库管理

**案例背景**:
- 用户: 独立开发者
- 视频规模: 500-1000 个家庭视频
- 硬件: 消费级 GPU (RTX 3060)
- 部署方式: Docker Compose

**使用体验**:
- ✅ 转录准确率高 (Whisper large-v3)
- ✅ 语义搜索效果好于关键词搜索
- ⚠️ 初次索引耗时长 (1小时视频需 15-20 分钟)
- ⚠️ ChromaDB 在 5000+ 视频后性能下降

**优化措施**:
- 调整采样间隔（从更密集采样改为更宽松采样，例如 2.5 秒或 5 秒，需按版本和素材复测）
- 禁用部分分析插件 (OCR、人脸识别)
- 使用 SSD 存储 ChromaDB 数据

**结论**: 适合小规模个人使用，需要合理配置

---

### 1.2 企业内部视频知识库

**案例背景**:
- 用户: 中小型企业
- 视频规模: 2000+ 培训视频、会议录像
- 硬件: 服务器 (96 核 CPU + 3×RTX 3090)
- 部署方式: Docker + Kubernetes

**使用体验**:
- ✅ 多用户并发访问稳定
- ✅ GPU 加速效果显著 (转录速度提升 5-8 倍)
- ✅ 语义搜索帮助员工快速找到培训内容
- ⚠️ PostgreSQL 需要定期维护 (VACUUM)
- ⚠️ ChromaDB 内存占用高 (20GB+)

**优化措施**:
- 增加 Redis 缓存容量
- 使用 PostgreSQL 连接池
- 定期清理旧的转录数据
- 配置 Nginx 反向代理

**结论**: 适合企业内部使用，需要专业运维

---

### 1.3 教育机构课程视频管理

**案例背景**:
- 用户: 在线教育平台
- 视频规模: 10000+ 课程视频
- 硬件: 云服务器 (AWS EC2 g4dn.xlarge)
- 部署方式: Docker + AWS ECS

**使用体验**:
- ✅ 学生可以通过自然语言搜索课程内容
- ✅ 自动生成视频摘要和章节标记
- ⚠️ ChromaDB 扩展性限制 (建议切换到 Qdrant)
- ⚠️ 云服务器成本高 (GPU 实例费用)

**优化措施**:
- 使用 Spot 实例降低成本
- 批量处理视频 (夜间低峰期)
- 缓存热门视频的搜索结果
- 使用 CloudFront CDN 加速访问

**结论**: 大规模使用需要架构优化和成本控制

## 5. 部署经验总结

### 5.1 硬件选择

**CPU**:
- 最低: 4 核 8 线程
- 推荐: 8 核 16 线程或更高
- 最佳: 16 核 32 线程 (支持高并发)

**GPU**:
- 最低: GTX 1660 (6GB VRAM)
- 推荐: RTX 3060 (12GB VRAM)
- 最佳: RTX 3090/4090 (24GB VRAM)

**内存**:
- 最低: 16GB
- 推荐: 32GB
- 最佳: 64GB+ (大规模部署)

**存储**:
- 系统盘: 100GB SSD
- 数据盘: 500GB+ SSD (视频数量而定)
- 数据库: NVMe SSD (提升性能)

---

### 5.2 软件配置

**Docker**:
- 使用 Docker Compose 简化部署
- 配置资源限制 (CPU、内存)
- 使用 Docker 卷持久化数据

**数据库**:
- PostgreSQL: 定期 VACUUM，配置连接池
- Redis: 配置持久化，监控内存使用
- ChromaDB: 使用 SSD 存储，定期备份

**AI 模型**:
- Whisper: 根据硬件选择模型大小 (tiny/base/small/medium/large)
- YOLO: 使用 YOLOv8s 平衡速度和准确率
- Embedding: 选择合适的模型 (all-MiniLM-L6-v2 vs text-embedding-ada-002)

---

### 5.3 性能优化

**并发配置**:
```env
MAX_CONCURRENT_TRANSCRIPTIONS=1  # 先跑通，再逐步提升到 2
MAX_CONCURRENT_ANALYSES=1        # 先跑通，再逐步提升到 2
```

**采样间隔**:
当前仓库若要调整采样间隔，需要修改 Python 服务启动参数或对应代码配置；
它不是当前 `.env` 中可直接生效的环境变量。

**插件选择**:
- 禁用不需要的插件 (OCR、人脸识别)
- 优先使用轻量级插件

**缓存策略**:
- Redis 缓存热门搜索结果
- 浏览器缓存静态资源
- CDN 加速视频访问

---

### 5.4 常见问题

**问题 1: 转录速度慢**
- 原因: GPU 未启用或模型过大
- 解决: 使用 docker-compose.cuda.yml，选择合适的 Whisper 模型

**问题 2: 搜索结果不准确**
- 原因: Embedding 模型不匹配或数据质量差
- 解决: 使用更好的 Embedding 模型，清理低质量数据

**问题 3: 内存占用高**
- 原因: ChromaDB 加载所有数据到内存
- 解决: 先确认是否真是向量库成为瓶颈；若未来独立实施替代向量库，再评估 Qdrant 或 Milvus

**问题 4: 磁盘空间不足**
- 原因: 缩略图、数据库、模型缓存占用大
- 解决: 定期清理，配置保留策略

## 6. 最佳实践

### 6.1 小规模部署 (<1000 视频)

**推荐方案**: Edit Mind + Docker Compose
- 硬件: 8 核 CPU + RTX 3060 + 32GB RAM
- 配置: 默认配置即可
- 成本: 一次性硬件投入 $1500-2000

---

### 6.2 中等规模部署 (1000-5000 视频)

**推荐方案**: Edit Mind + Docker Compose + 压测/监控
- 硬件: 16 核 CPU + RTX 3090 + 64GB RAM
- 配置: 提高并发数，建立基线压测，持续观察 Chroma 是否真的成为瓶颈
- 成本: 一次性硬件投入 $3000-4000

---

### 6.3 大规模部署 (>5000 视频)

**推荐方案**: 自定义架构 + Kubernetes
- 硬件: 多节点集群 (CPU + GPU 节点)
- 配置: 分布式部署，使用 Milvus 或 Weaviate
- 成本: 硬件 + 运维成本 $10000+

---

## 7. 成本对比

### 7.1 自托管 vs 商业 API

**场景**: 1000 小时视频/年

**自托管 (Edit Mind)**:
- 硬件: $3000 (一次性)
- 电费: $200/年 (24/7 运行)
- 总成本: $3200 (第一年)，$200/年 (后续)

**商业 API (Google Video Intelligence)**:
- 转录: $6000/年
- 分析: $6000/年
- 总成本: $12000/年

**结论**: 自托管第一年节省 $8800，后续每年节省 $11800

## 8. 结论与建议

### 8.1 适合自托管的场景

- ✅ 视频规模 <5000 个
- ✅ 有一定技术能力
- ✅ 注重数据隐私
- ✅ 预算有限

### 8.2 适合商业 API 的场景

- ✅ 视频规模 >10000 个
- ✅ 需要高可用性
- ✅ 无运维能力
- ✅ 预算充足

### 8.3 最终建议

**对于个人用户**: 使用 Edit Mind 或 Immich
**对于中小企业**: 使用 Edit Mind + 专业运维
**对于大型企业**: 使用商业 API 或自建分布式系统
