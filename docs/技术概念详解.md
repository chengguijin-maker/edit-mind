## 核心概念

### 什么是 Edit Mind？

**简单理解**：Edit Mind 就像是给你的视频库配备了一个"超级管家"。

**类比**：
- 传统方式：你有 1000 个视频文件，想找"那个有猫的视频"，只能一个个打开看
- Edit Mind：你说"找有猫的视频"，它立刻告诉你是哪几个，甚至精确到第几分钟

**核心功能**：
1. **视频索引**：给每个视频建立"档案"
2. **AI 分析**：理解视频内容（说了什么、出现了什么）
3. **语义搜索**：用自然语言搜索（不需要记住文件名）

## 容器化技术

### Docker（码头工人）

**是什么**：Docker 是一个"软件打包工具"。

**生活类比**：
```
传统安装软件 = 搬家
- 需要准备各种家具（依赖）
- 不同房子（电脑）可能装不下
- 搬家很麻烦

Docker = 集装箱
- 把所有东西打包在一个箱子里
- 任何地方都能用
- 搬运方便
```

**在 Edit Mind 中的作用**：
```
Edit Mind 包含 6 个"集装箱"（容器）：

1. Web 容器 - 网页界面
2. Background Jobs 容器 - 后台任务处理
3. PostgreSQL 容器 - 数据库
4. Redis 容器 - 缓存
5. ChromaDB 容器 - 向量数据库
6. ML 容器 - AI 处理
```

**为什么用 Docker**：
- ✅ 不用担心"我的电脑能不能运行"
- ✅ 一键启动所有服务
- ✅ 环境隔离，不会污染系统

### Docker Compose（指挥官）

**是什么**：管理多个 Docker 容器的工具。

**类比**：
```
Docker = 单个集装箱
Docker Compose = 集装箱码头管理系统

一个命令启动所有容器：
docker compose up
```

**在项目中的配置文件**：
- `docker-compose.yml` - 标准版（CPU）
- `docker-compose.cuda.yml` - GPU 加速版

## 数据库技术

### PostgreSQL（关系型数据库）

**是什么**：一个存储结构化数据的数据库。

**生活类比**：
```
PostgreSQL = Excel 表格（但更强大）

视频表：
| ID | 文件名 | 时长 | 创建时间 |
|----|--------|------|----------|
| 1  | cat.mp4| 120s | 2026-03-10 |
| 2  | dog.mp4| 180s | 2026-03-09 |

用户表：
| ID | 邮箱 | 密码 |
|----|------|------|
| 1  | admin@example.com | *** |
```

**在 Edit Mind 中存储**：
- 视频元数据（文件名、大小、时长）
- 用户信息
- 文件夹结构
- 任务状态

**为什么用 PostgreSQL**：
- ✅ 可靠性高
- ✅ 支持复杂查询
- ✅ 开源免费

### Redis（缓存数据库）

**是什么**：一个超快的内存数据库。

**生活类比**：
```
PostgreSQL = 图书馆（慢但容量大）
Redis = 你的书桌（快但空间小）

常用的书放桌上（Redis）
不常用的放图书馆（PostgreSQL）
```

**在 Edit Mind 中的作用**：
1. **任务队列**：存储待处理的视频任务
2. **会话缓存**：记住用户登录状态
3. **临时数据**：加速频繁访问的数据

**为什么用 Redis**：
- ✅ 速度极快（内存操作）
- ✅ 支持队列功能
- ✅ 适合临时数据

### ChromaDB（向量数据库）

**是什么**：专门存储"向量"（数字数组）的数据库。

**什么是向量**：
```
文字 "猫" → AI 转换 → [0.2, 0.8, 0.1, ...] (512 个数字)
图片 🐱  → AI 转换 → [0.3, 0.7, 0.2, ...] (512 个数字)

相似的内容 → 相似的数字
```

**生活类比**：
```
传统搜索 = 查字典
- 必须输入准确的词
- "猫" 找不到 "cat"

向量搜索 = 找相似的东西
- 输入 "猫"
- 能找到 "小猫"、"猫咪"、"喵星人"
- 甚至能找到猫的图片
```

**在 Edit Mind 中存储**：
- 视频转录文本的向量
- 视频帧（画面）的向量
- 用于语义搜索

**为什么用 ChromaDB**：
- ✅ 专为 AI 搜索设计
- ✅ 支持相似度搜索
- ✅ 易于使用

## AI/ML 技术

### 什么是 AI/ML？

**AI (Artificial Intelligence)**：人工智能，让计算机模拟人类智能。
**ML (Machine Learning)**：机器学习，AI 的一种实现方式。

**简单理解**：
```
传统程序 = 菜谱
- 步骤 1：切菜
- 步骤 2：炒菜
- 步骤 3：装盘

AI/ML = 学习做菜
- 看 1000 个做菜视频
- 自己总结规律
- 能做出新菜
```

### Whisper（语音识别）

**是什么**：OpenAI 开发的语音转文字模型。

**功能**：
```
视频音频 → Whisper → 文字稿

例如：
音频："今天天气真好"
输出："今天天气真好"（带时间戳）
```

**在 Edit Mind 中的作用**：
- 提取视频中的对话
- 生成字幕
- 用于搜索视频内容

**为什么用 Whisper**：
- ✅ 准确率高
- ✅ 支持多语言
- ✅ 开源免费

### YOLO（物体检测）

**是什么**：一个识别图片/视频中物体的模型。

**功能**：
```
视频帧 → YOLO → 识别结果

例如：
画面：[一只猫坐在沙发上]
输出：
- 猫（置信度 95%）
- 沙发（置信度 92%）
```

**在 Edit Mind 中的作用**：
- 识别视频中的物体
- 场景分析
- 用于搜索"有猫的视频"

### DeepFace（人脸识别）

**是什么**：人脸识别和分析模型。

**功能**：
```
视频帧 → DeepFace → 人脸信息

例如：
画面：[一个人的脸]
输出：
- 检测到人脸
- 特征向量（用于识别是谁）
- 年龄、性别、情绪（可选）
```

**在 Edit Mind 中的作用**：
- 识别视频中的人物
- 按人物分类视频
- 搜索"某个人出现的视频"

### PyTorch（深度学习框架）

**是什么**：一个用于构建和运行 AI 模型的工具库。

**类比**：
```
AI 模型 = 汽车
PyTorch = 汽车制造厂

提供：
- 零件（神经网络层）
- 工具（训练算法）
- 说明书（文档）
```

**在 Edit Mind 中的作用**：
- 运行 Whisper、YOLO、DeepFace
- 提供 GPU 加速支持

### Embedding（嵌入/向量化）

**是什么**：把文字、图片、音频转换成数字向量的过程。

**详细解释**：
```
原始数据 → AI 模型 → 向量（数字数组）

文字 "猫" → [0.2, 0.8, 0.1, 0.5, ...]
文字 "狗" → [0.3, 0.7, 0.2, 0.4, ...]
文字 "汽车" → [0.9, 0.1, 0.8, 0.2, ...]

相似的概念 → 向量距离近
"猫" 和 "狗" 的向量距离 < "猫" 和 "汽车"
```

**在 Edit Mind 中的流程**：
```
1. 视频转录 → 文字
2. 文字 → Embedding → 文字向量
3. 视频帧 → Embedding → 图像向量
4. 存入 ChromaDB
5. 搜索时：查询词 → 向量 → 找相似向量
```

### GPU 加速

**是什么**：使用显卡（GPU）加速 AI 计算。

**CPU vs GPU**：
```
CPU = 1 个超级聪明的人
- 一次做一件事
- 但做得很快很好

GPU = 1000 个普通人
- 同时做 1000 件事
- 适合重复性工作

AI 计算 = 大量重复计算
→ GPU 快 10-100 倍
```

**在 Edit Mind 中**：
- CPU 版本：慢但兼容性好
- GPU 版本（CUDA）：快 5-10 倍

**CUDA**：NVIDIA 显卡的 GPU 编程接口。

## 前端技术

### React（前端框架）

**是什么**：构建用户界面的 JavaScript 库。

**类比**：
```
传统网页 = 静态海报
- 内容固定
- 要改就重新印

React = 电子屏幕
- 内容动态变化
- 交互流畅
```

**在 Edit Mind 中**：
- 视频列表界面
- 搜索界面
- 播放器界面

### React Router（路由）

**是什么**：管理页面跳转的工具。

**功能**：
```
/videos → 视频列表页
/search → 搜索页
/settings → 设置页

点击链接 → 切换页面（不刷新）
```

### Vite（构建工具）

**是什么**：快速的前端构建工具。

**功能**：
- 开发时：热更新（改代码立即生效）
- 打包时：优化代码（压缩、合并）

### TypeScript

**是什么**：带类型检查的 JavaScript。

**类比**：
```
JavaScript = 自由写作
- 想写什么写什么
- 容易出错

TypeScript = 有格式要求的写作
- 必须声明变量类型
- 编译时发现错误
```

**例子**：
```typescript
// JavaScript（可能出错）
function add(a, b) {
  return a + b;
}
add("1", 2); // "12" (字符串拼接，不是数学加法)

// TypeScript（编译时报错）
function add(a: number, b: number): number {
  return a + b;
}
add("1", 2); // ❌ 编译错误：类型不匹配
```

## 后端技术

### Node.js

**是什么**：在服务器端运行 JavaScript 的环境。

**类比**：
```
浏览器 = JavaScript 的家
Node.js = 让 JavaScript 搬到服务器

可以做：
- 处理文件
- 操作数据库
- 提供 API
```

### Express.js（Web 框架）

**是什么**：Node.js 的 Web 服务器框架。

**功能**：
```
客户端请求 → Express 处理 → 返回响应

GET /api/videos → 返回视频列表
POST /api/folders → 添加索引文件夹
```

### BullMQ（任务队列）

**是什么**：管理后台任务的队列系统。

**生活类比**：
```
BullMQ = 餐厅的点单系统

1. 顾客点餐（添加任务）
2. 订单进入队列
3. 厨师按顺序做菜（处理任务）
4. 做好了通知顾客（任务完成）
```

**在 Edit Mind 中**：
```
任务类型：
1. 视频转录任务
2. 视频分析任务
3. 嵌入生成任务

流程：
用户添加文件夹 / 触发重扫 → 创建任务 → 加入队列 → Worker 处理
```

### WebSocket（实时通信）

**是什么**：浏览器和服务器之间的双向通信协议。

**HTTP vs WebSocket**：
```
HTTP = 写信
- 你问一句，服务器答一句
- 每次都要重新建立连接

WebSocket = 打电话
- 连接一次，持续通话
- 双方随时发消息
```

**在 Edit Mind 中**：
- 定期推送后台服务状态
- 作为实时能力基础设施支撑部分交互功能
- 当前任务列表和处理详情主要仍通过 API 读取

### Prisma（ORM）

**是什么**：数据库操作工具，让你用 JavaScript 操作数据库。

**传统 SQL vs Prisma**：
```sql
-- 传统 SQL（容易出错）
SELECT * FROM videos WHERE title LIKE '%cat%';

// Prisma（类型安全）
const videos = await prisma.video.findMany({
  where: {
    title: {
      contains: 'cat'
    }
  }
});
```

**优势**：
- ✅ 类型安全
- ✅ 自动补全
- ✅ 数据库迁移管理

## 完整工作流程

### 流程 1：用户添加文件夹并触发索引

```
┌─────────────┐
│ 1. 用户操作 │
└──────┬──────┘
       │ 添加媒体文件夹 / 点击 Rescan
       ↓
┌─────────────────┐
│ 2. Web 前端     │ (React Router)
│ - 调用 /api/folders
│ - 调用 /api/folders/:id/rescan
└────────┬────────┘
         │ 写入文件夹信息并转发内部请求
         ↓
┌──────────────────────┐
│ 3. PostgreSQL        │
│ - 保存 folder 元数据 │
│ - 保存 job 记录      │
└─────────┬────────────┘
          │
          ↓
┌──────────────────────┐
│ 4. Background Jobs   │ (Express + BullMQ)
│ - 扫描文件夹中的视频   │
│ - 为每个视频创建索引任务│
│ - 可启动文件系统 watcher│
└─────────┬────────────┘
          │ 任务入队
          ↓
┌─────────────────┐
│ 5. Redis / BullMQ│
│ - transcription │
│ - frame-analysis│
│ - scene-creation│
│ - 各类 embedding │
└────────┬────────┘
         │ Worker 取任务
         ↓
┌──────────────────────┐
│ 6. Python ML 服务    │
│ - Whisper 转录音频   │
│ - 多插件逐帧分析     │
└─────────┬────────────┘
          │
          ↓
┌──────────────────────┐
│ 7. Scene + Embedding │
│ - 先生成 scenes      │
│ - 再并行做 text/audio│
│   /visual embedding  │
└─────────┬────────────┘
          │
          ↓
┌─────────────────┐
│ 8. ChromaDB     │
│ - video_content │
│ - _visual       │
│ - _audio        │
└────────┬────────┘
         │
         ↓
┌─────────────────┐
│ 9. 前端查看状态 │
│ - /api/jobs     │
│ - /api/folders/*│
│ - Socket.IO 主看│
│   service-status│
└─────────────────┘
```

补充说明：

- 当前索引入口是“文件夹”，不是直接把单个视频文件上传到后台服务。
- `background-jobs` 在重扫时会扫描目录、创建 `Job` 记录，并把任务送入 BullMQ。
- 如果文件夹启用了 watcher，新视频文件写入后也会自动创建索引任务。

### 流程 2：用户搜索视频

```
┌─────────────┐
│ 1. 用户输入 │
└──────┬──────┘
       │ "有猫的视频" / 上传参考图片
       ↓
┌─────────────────┐
│ 2. Web 前端     │
│ - 调用 /api/search
│ - 或 /api/search/image
└────────┬────────┘
         │ 进入 Web 路由 action
         ↓
┌──────────────────────┐
│ 3. Search 包         │
│ - 解析查询条件       │
│ - 构造文本/图片检索   │
└─────────┬────────────┘
          │ 查询向量集合
          ↓
┌─────────────────┐
│ 4. ChromaDB     │
│ - 语义召回 scene│
│ - 返回候选结果   │
└────────┬────────┘
         │ 补全结构化信息
         ↓
┌──────────────────────┐
│ 5. PostgreSQL        │
│ - 查询视频 / scene   │
│ - 补足元数据         │
└─────────┬────────────┘
          │
          ↓
┌─────────────────┐
│ 6. 返回结果     │
│ - 视频列表      │
│ - 相关片段      │
│ - 相关度分数    │
└─────────────────┘
```

补充说明：

- 正常搜索链路由 `web` 直接处理，不需要经过 `background-jobs` 中转。
- 图片搜索会把图片检索结果和文本检索结果做混排。

### 流程 3：视频处理详细步骤

#### 步骤 1：视频转录（Whisper）

```
输入：video.mp4
     ↓
提取音频 / 读取音轨
     ↓
Whisper 模型处理
     ↓
输出：
{
  "text": "今天天气真好",
  "segments": [
    {
      "start": 0.0,
      "end": 2.5,
      "text": "今天天气真好"
    }
  ]
}
```

#### 步骤 2：逐帧分析（多插件串行）

```
输入：video.mp4
     ↓
默认每 5 秒采样 1 帧
     ↓
对每个采样帧依次执行插件：
     ├─→ ObjectDetectionPlugin
     ├─→ FaceRecognitionPlugin
     ├─→ ShotTypePlugin
     ├─→ DominantColorPlugin
     ├─→ DescriptorPlugin
     └─→ TextDetectionPlugin
     ↓
汇总为结构化 frame analysis
```

这里要特别注意：

- 当前并不是“每秒 1 帧”。
- 单帧上的多个插件是顺序执行，不是把所有插件完全并行展开。
- 部分插件可以按 skip interval 降低执行频率，但关键插件仍会频繁运行。

#### 步骤 3：Scene 创建

```
转录结果 + frame analysis
          ↓
createScenes(...)
          ↓
得到按时间片组织的 scenes
```

场景创建发生在 embedding 之前，这是后续多模态索引的基础。

#### 步骤 4：生成三类嵌入向量

```
scenes
  ├─→ 文本 embedding
  ├─→ 视觉 embedding
  └─→ 音频 embedding
          ↓
写入 ChromaDB：
  - video_content
  - video_content_visual
  - video_content_audio
```

这一步不是把数据写到 `transcripts`、`frames`、`objects` 这类集合名中，而是写到当前代码真实创建的三个 collection。

#### 步骤 5：完成入库与展示

```
embedding 完成
     ↓
video-finalization
     ↓
更新 PostgreSQL 中的 job / video / scene 状态
     ↓
前端通过 API 查看处理结果
```

## 常见问题解答

### Q1: 为什么需要这么多技术？

**A**: 每个技术解决特定问题：

```
问题                    解决方案
─────────────────────────────────────
视频太多找不到          → AI 分析 + 语义搜索
处理速度慢              → 任务队列 + GPU 加速
数据量大                → 数据库 + 向量数据库
用户体验差              → React + API + Socket.IO
部署困难                → Docker 容器化
```

### Q2: 什么是"语义搜索"？

**A**: 理解意思的搜索，不是简单的关键词匹配。

```
传统搜索（关键词匹配）：
搜索 "猫" → 只找文件名或标签包含 "猫" 的视频

语义搜索（理解意思）：
搜索 "猫" → 找到：
- 文件名有 "猫" 的
- 转录中提到 "猫" 的
- 画面中有猫的
- 甚至提到 "喵星人"、"小猫咪" 的
```

### Q3: GPU 加速有多重要？

**A**: 很重要，但不能把它理解成“只要有强 GPU，端到端就一定很快”。

```
GPU 通常会明显加速：
- Whisper 转录
- YOLO / 人脸等视觉推理
- 其他依赖深度学习的阶段

但实际端到端耗时还受这些因素影响：
- 默认每 5 秒采样 1 帧
- 每帧要顺序跑多个分析插件
- scene 创建后还有 text/audio/visual embedding
- audio / visual embedding 当前默认 worker 并发是 2

所以更准确的说法是：
- GPU 往往能带来明显收益
- 真实提速倍数强依赖素材和配置
- 需要结合你的视频样本做实测，不能把某个固定分钟数当成通用承诺
```

### Q4: 为什么要用 Docker？

**A**: 简化部署，避免环境问题。

```
不用 Docker：
1. 安装 Node.js 22
2. 安装 Python 3.11
3. 安装 PostgreSQL
4. 安装 Redis
5. 安装 ChromaDB
6. 配置环境变量
7. 安装 CUDA（如果用 GPU）
8. 安装各种依赖
9. 可能遇到版本冲突
10. 可能遇到系统兼容性问题

用 Docker：
1. docker compose up
（完成）
```

### Q5: 数据存在哪里？

**A**: 分层存储。

```
原始视频文件：
→ 你的硬盘（HOST_MEDIA_PATH）

视频元数据：
→ PostgreSQL 数据库

AI 分析结果：
→ PostgreSQL（结构化数据）
→ ChromaDB（向量数据）

临时文件：
→ .data 目录
  ├── .thumbnails/（缩略图）
  ├── .faces/（人脸数据）
  └── .stitched-videos/（拼接视频）

ML 模型：
→ ml-models 卷
  ├── whisper/（Whisper 模型）
  ├── ultralytics/（YOLO 模型）
  └── deepface/（DeepFace 模型）
```

### Q6: 如何理解"向量"？

**A**: 向量是内容的数字指纹。

```
文字 "猫" 的向量（简化版）：
[0.8, 0.2, 0.1, 0.9, 0.3, ...]
 ↑    ↑    ↑    ↑    ↑
 动物 可爱 小型 毛茸茸 宠物

文字 "狗" 的向量：
[0.7, 0.3, 0.2, 0.8, 0.4, ...]
 ↑    ↑    ↑    ↑    ↑
 动物 可爱 中型 毛茸茸 宠物

文字 "汽车" 的向量：
[0.1, 0.0, 0.9, 0.0, 0.1, ...]
 ↑    ↑    ↑    ↑    ↑
 非动物 不可爱 大型 金属 交通工具

"猫" 和 "狗" 的向量相似
→ 搜索 "猫" 也能找到 "狗"

"猫" 和 "汽车" 的向量差异大
→ 搜索 "猫" 不会找到 "汽车"
```

## 性能优化建议

### 1. 充分利用硬件

**您的配置**：
- 96 核 CPU
- 3 × RTX 3090 GPU
- 313 GB 内存

**优化配置**：
```ini
# 先从保守值开始
MAX_CONCURRENT_TRANSCRIPTIONS="1"
MAX_CONCURRENT_ANALYSES="1"
```

**建议策略**：
```
先跑通单视频 / 单任务
     ↓
观察 CPU / GPU / Redis / PostgreSQL / Chroma 占用
     ↓
再逐步提高到 2 或 4
     ↓
结合真实素材继续压测
```

原因是：

- Node 侧并发提高，不代表 Python 侧真实吞吐同步提高
- `audio-embedding` 和 `visual-embedding` 当前默认并发是 `2`
- 过早把并发拉高，容易把问题从“慢”变成“排队卡住”

### 2. 使用 GPU 加速

```bash
# 使用 CUDA 版本
docker compose -f docker-compose.cuda.yml up -d
```

**注意点**：
```
先确认 Docker GPU 运行时可用
再对比同一批素材的真实处理时间
不要把单次经验值当成固定 SLA
```

### 3. 监控资源使用

```bash
# 监控 Docker 容器
docker stats

# 监控 GPU
watch -n 1 nvidia-smi

# 监控磁盘
df -h
```

## 故障排查指南

### 问题 1：容器启动失败

**症状**：`docker compose up` 报错

**可能原因**：
1. 端口被占用
2. 环境变量未配置
3. 磁盘空间不足

**解决方法**：
```bash
# 检查端口
sudo lsof -i :3745 -i :4000 -i :5432 -i :6379 -i :8000 -i :8765

# 检查环境变量
cat .env | grep -E 'SESSION_SECRET|ENCRYPTION_KEY|HOST_MEDIA_PATH'

# 检查磁盘空间
df -h
```

### 问题 2：视频处理很慢

**症状**：视频处理时间过长

**可能原因**：
1. 使用 CPU 模式
2. 并发数设置太低
3. GPU 未正确配置

**解决方法**：
```bash
# 检查是否使用 GPU
docker compose ps | grep ml

# 如果是 CPU 版本，切换到 GPU 版本
docker compose down
docker compose -f docker-compose.cuda.yml up -d

# 先确认单任务能稳定完成，再小步上调并发
# 建议从 1 调到 2，观察后再继续增加
```

### 问题 3：搜索结果不准确

**症状**：搜索找不到相关视频

**可能原因**：
1. 视频还未处理完成
2. 嵌入向量未生成
3. AI 模型未正确配置

**解决方法**：
```bash
# 检查任务状态
docker compose logs background-jobs | grep -i "processing"

# 检查 ChromaDB
docker compose logs chroma

# 重新处理视频
# 在 Web 界面点击 "Rescan" 按钮
```
